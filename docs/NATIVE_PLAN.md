# Native system application correction

The first implementation used a local web dashboard inside WKWebView. The user requires system applications. Replace this shell with two native macOS clients; retain the tested Python engine as a private local service.

1. Relay: primary native menu-bar Liquid Glass popover, plus SwiftUI session browser and inspector, native search and provider/state filters, parent/child relationships, local naming and explicit Codex title sync, clipboard resume/Claude rename commands, native menu-bar activity and attention items. Show evidence provenance and unavailable fields. Live and labelled synthetic modes.
2. Repro: separate native menu-bar application with a quick glass popover and expanded SwiftUI workspace. Native repository folder picker, issue editor, generator selection, asynchronous job status, multiline generated test, baseline and verification evidence, explicit source-fix verification, demo fix only on disposable fixture, native save dialog for evidence ZIP.
3. Shared engine client: typed local API models, background engine launch and retry, GUI-safe tool PATH. No HTML rendering, WebKit, browser launch, or hosted service needed for either app.
4. Two Claude Code Haiku workers own the two client files. Parent owns shared client, packaging, integration, and verification. Use safe mode with normal OAuth; bare mode excludes OAuth and was the wrong invocation.
5. Build both bundles with swiftc, inspect both real native windows, exercise synthetic naming and Docker Repro end to end, run existing engine regressions. Keep developer build dependency on checkout documented; no claim of a portable signed distribution.

The web dashboard remains only a developer diagnostic surface. It is no longer the application UI.
